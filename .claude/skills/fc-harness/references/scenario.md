# Как писать сценарий харнеса

Сценарий — `tests/<что-проверяем>.txt`, по шагу в строке, `#` — комментарий. Полный синтаксис шагов — шапка `tools/harness/test.go`.

## Шаблон

```
# <Карта>: <что должно быть у клиента, одной фразой>. <Как было до фикса, с датой и числами:
# "2026-10-30: client rotorOn 0 while the server had 1">.
# Run from the repo root: tools/bin/harness.exe test tests/<имя>.txt
up -mode host -map <карта> -clients 1 -mod FarCryCoop -asi tools/bin/FarCryCoopNet.asi -start #COOP_ExpectPlayers=2;#CoopMap("<карта>")
wait server players>=2 -t 60s
wait client1 players>=2 -t 120s
sleep 5s
# состояние ДО действия — чтобы сценарий не был зелёным случайно
expect client1 <код> => <значение до>
# действие на сервере
lua server <код>
sleep <сколько нужно, чтобы дошло>
expect server <код> => <ожидаемое>
expect client1 <код> => <ожидаемое>
# поздно подключившийся клиент получает то же (если это состояние, а не событие)
cmd client1 reconnect
sleep 5s
wait client1 players>=2 -t 120s
sleep 20s
expect client1 <код> => <ожидаемое>
expect-no-events
down
```

Комментарии и имена — по-английски (они в публичном репозитории рядом с кодом).

## Шаги, которые чаще всего нужны

- `wait <inst> players>=2 -t 120s` — условие по `state.txt` агента. Поля: `level`, `players`, `ai`, `ai.alive`, `ents`, `me.health`, `server`, `client`, `lastseq`.
- `expect <inst> <код> => <значение>` — `return <код>` должен дать ровно это (строкой). Булево приводи так: `(<условие>) and 1 => 1`.
- `expect-log <inst> <regex> [таймаут]` — в логе экземпляра есть совпадение. Пробелы в regex пишутся точкой: `hud.msg.client1.has.entered`. Удобно ловить события `CoopMonEvent` — строки `MON C t=… <текст>` в логе клиента (`heli rotor Gunship1 1`, `sequence …`, `hud …`).
- `expect-diff max=<м> [class=<re>] [exclude=<re>] [missing=0]` — сравнение всех сущностей клиента с сервером: позиция и здоровье. `missing=0` — множества сущностей должны совпасть. Используй узкий `class=`, а `exclude=` только для записанных открытых проблем с комментарием, почему.
- `expect-no-events` — ни крэша, ни диалога ошибки, ни зависшего агента.
- `cmd client1 reconnect` — переподключение клиента (проверка «поздно зашедшего»).

## Помощники агента и мода

- `Harness:RemotePlayer()` (на сервере — игрок клиента), `Harness:Player("client1")`, `Harness:Loadout(P)` — снаряжение одной строкой, одинаковое на сервере и у клиента.
- `COOP_God=1` на сервере — игроки не умирают (иначе скрипты провала миссии мешают), но и здоровье у них всегда полное.
- `CoopMovePlayer(Harness:RemotePlayer(), {x=…,y=…,z=…})` — переместить удалённого игрока (не `SetPos`).
- `CoopGoto(<n>)` — прыгнуть к чекпоинту `n`; `CoopGoto()` печатает в лог сервера список `checkpoint <n> at …`.
- `Harness:Use()` — нажать «использовать» на этом экземпляре (как клавиша F; через ASI). На клиенте нажатие уходит на сервер со следующей командой: `expect client1 Harness:Use() => ok`, потом `sleep 2s` и проверка на сервере. Клавиатуру Lua и `SendInput` в окно не нажимают.
- Сущность по имени: `System:GetEntityByName("Gunship1")`; по id: `System:GetEntity(770)`. Имена смотри в логе или через `harness lua server "…"` на живом прогоне (`test -keep`).

## Предусловия: действие должно случиться на сервере

Прежде чем проверять клиента, убедись, что действие вообще происходит на сервере, и проверь это отдельным `expect server` (иначе красный клиент значит «ничего не было», а не баг синхронизации). Открой ванильный скрипт сущности в `Scripts.pak` и посмотри условия (пример: аптечка берётся только при `health < max_health`, `PICKUPS/health.lua`). Мод сам меняет часть состояния — `COOP/gamerules.lua`, `OnUpdate`:

- `COOP_God=1` доливает здоровье каждый кадр;
- пока ждут игроков (`COOP_WaitDone` ещё нет) и пока у хоста выключен HUD (катсцена, `cl_display_hud 0`), здоровье тоже доливается;
- поэтому для проверок со здоровьем: пропусти интро голосованием (`CoopSkipVote()` у сервера и клиента, `expect-log server cutscene.skipped.by.2.of.2`), сними god и ставь здоровье тем же `lua`-шагом, что и действие.

Образцы: `tests/skip-vote.txt` (пропуск интро), `tests/pickups.txt` (подбор удалённым игроком).

## Чтобы сценарий ловил именно баг

1. Сначала прогони его на текущем коде: он должен **упасть**, и упасть на том шаге, который описывает баг. Запиши в шапку, что было до фикса.
2. Проверь состояние до действия (`expect … => <до>`), иначе зелёный может значить «ничего не произошло ни там, ни там».
3. Ждать — `wait`/`expect-log` с таймаутом, а `sleep` — только когда ждать нечего по состоянию (дошла ли команда до клиента).
4. Если баг плавающий, сценарий должен падать хотя бы в части прогонов — замерь «k из N» (`run-suite.sh -n 10 <имя>`) до фикса.
5. Пока проблема не решена, но сценарий уже нужен, поставь в шапку `# OPEN: fails until fixed.` — `run-suite.sh` покажет его как `open`, а не регрессию.
