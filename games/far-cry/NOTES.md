## Spike 1 — campaign map as a network server (2026-10-18, works)

Run from the install in `D:` (owner's one-time exception to the copy rule; the game rewrote its own `log.txt` / `log_WinSV.txt` there, no files were changed by us).

Steps that worked:
1. `Bin32\FarCry_WinSV.exe -DEVMODE` (Lua `#` console commands work only with `-DEVMODE`; console input line is limited to roughly 100 characters).
2. In the server console, after the banner (commands passed on the command line run too early and are ignored):
   ```
   #AvailableMODList.DEFAULT={team=0,respawntime=0,mission="Training"}
   g_GameType DEFAULT
   start_server Training
   ```
   `start_server` takes the mission from `AvailableMODList[g_GameType]`; `Game:CheckMap("Training","Training")` is 1, with `"Default"` it is nil.
3. Client: plain `Bin32\FarCry.exe`, Multiplayer -> LAN -> join. (Passing `"connect 127.0.0.1"` or `r_Width` on the command line made the client shut down right after init; typing `connect` in the main-menu console did nothing.)

Result: the server loaded `Training` with the single-player `GameRules` (655 entities). The client got slot 1, a player entity at the first respawn point with 255 health, the normal HUD, and could walk, shoot and play. Two processes (dedicated server + client) run on one PC.

Still unchecked: mission objectives, AI behaviour, cut scenes, checkpoints, a second remote player.

## Spike 2 — weapons broken for the remote client (2026-10-18, root cause found)

Symptom on campaign maps (both `DEFAULT` and `FFA` rules): the remote client can walk, run and jump, but has no weapon model, cannot fire (endless reload), and crouch is not shown. Stock `mp_airstrip` + `ASSAULT` works fully.

Evidence (server tracer `GameRules:OnUpdate` hook, client tracer `ClientStuff.OnUpdate` hook, one line per second):
- Server receives everything: crouch (`crouching=1`), fire (`firing=1`), weapon switches, damage, respawn.
- Client on `mp_airstrip`: weapon 19, clip 50, ammo 100, `canfire=1`, `drawfpweapon=1`.
- Client on `Pier`: weapon 19 (P90), clip 0, ammo 0, `canfire=nil`, `drawfpweapon=nil`; the server meanwhile already switched to weapon 12 (MP5).

Root cause: a level loads weapon classes from its mission XML `<Weapons><Used>` list (`CXSystemBase::LoadXMLNode` -> `CWeaponSystemEx::AddWeapon`). MP missions list every weapon; campaign missions list only a few (`Pier`: Falcon, M4, Machete, SniperRifle). On the server, missing classes are loaded on demand by `BasicPlayer:ScriptInitWeapon` -> `Game:AddWeapon`; the remote client never does this, so `CPlayer::Read` -> `SelectWeapon` fails for unloaded classes.

Fix direction (for the mod): client-side co-op script loads every class from `WeaponClassesEx` (`Scripts\Default\Entities\Weapons\WeaponSystem.lua`) at level load, before the local player is spawned. A runtime test from the console (`Game:AddWeapon` for all classes after spawn) gave the first-person weapon back (`drawfpweapon=1`) but not ammo/fire, so it must happen before the player is set up.

Also seen: switching the map on the server drops the client back to the menu; the campaign intro cut scene does not play for the client; FC1 console input is cut at about 100 characters (use `#dofile("E:/...")` for longer Lua).

## Spike 4 — ASI logger finds where updates are lost (2026-10-18)

Plugin: `games/far-cry/asi/FarCryCoopNet.c`, built by `asi/build.ps1` (VS 2022 x86, no Windows SDK and no CRT: import libraries come from stub DLLs). Installed as `Bin32\FarCryCoopNet.asi` (owner allowed this one file), loaded by `version.dll` in both `FarCry.exe` and `FarCry_WinSV.exe`. It checks the `CryGame.dll` PE timestamp `0x44e2f64d`, hooks by address and writes a once-per-second summary to `Mods\FarCryCoop\netlog_<exe>_<pid>.txt`.

Addresses in `CryGame.dll` 1.4.0.1405 (image base `0x33000000`, found with REA/Ghidra and checked against SDK sources):

| Function | Address | Calling convention / notes |
|---|---|---|
| `CXSnapshot::BuildAndSendSnapshot` | `0x3306faba` | thiscall, no arguments; anchor string `netentities %d/%d` |
| `CNetEntityInfo::Update(Vec3)` | `0x330bb9b7` | thiscall, `ret 0xc`; `+0x04` m_pEntity, `+0x1c` m_nPriority |
| `CNetEntityInfo::Write(CXServer*, CStream&)` | `0x330bb82d` | thiscall, `ret 8` |
| `CXClient::OnServerMsgTimeStamp(CStream&)` | `0x33080227` | thiscall, `ret 4` |
| `CXClient::OnServerMsgUpdateEntity(CStream&)` | `0x330816ef` | thiscall, `ret 4`; anchor `error reading from the snapshot` |
| `CXClient::ParseIncomingStream` (message switch) | `0x3308354b` | `false` from UpdateEntity drops the rest of the packet |
| `GameWarning` | `0x3307019e` | cdecl, varargs |

`CXClient` fields: `+0x0c` m_wPlayerID, `+0x10` m_iPhysicalWorldTime, `+0x14` m_bIgnoreSnapshot, `+0x40` m_bLocalHost, `+0x44` m_pGame, `+0x4c` m_pISystem. `CStream`: `+0x470` size in bits, `+0x474` read position.

Result on `Pier` (COOP, `sv_maxrate*` 10000000):
- Server: ~17 snapshots/s, 550 net entities, 442 of them priority 0, ~108 actually written per snapshot (1836/s), the slot player (id 65489, priority 1.1 million) in every snapshot, ~18 000 bits per snapshot.
- Client: TimeStamp 17/s, `m_bIgnoreSnapshot` never set, ~63 `UpdateEntity` per snapshot (~1080/s), 0 failures, no "not spawned" warnings. `m_wPlayerID` = 65489 matches the server, but not one update for 65489 arrives.

Conclusion: CryGame on both sides works; ~40% of every snapshot (its tail) is lost between `CXServerSlot::SendUnreliableMsg` -> `m_pISSlot->SendUnreliable` (CryNetwork.dll) and the client. The own player was spawned last, sits at the end of `m_lstNetEntities` and is always in the lost tail; AI at the end of the list freeze the same way. `mp_airstrip` has few entities, so its snapshot fits. Likely the unreliable packet has a size limit (~10 000 bits arrive) and the rest is dropped. Our `sv_maxrate*` = 10000000 makes it worse: the priority threshold falls to ~0 and every candidate is sent.

Fix 1 (done, in the ASI): before every `BuildAndSendSnapshot` the plugin sorts `m_lstNetEntities` by `m_nPriority * time since last send` (std::list node: `+0` next, `+4` prev, `+8` CNetEntityInfo with `+0x10` m_fLastUpdate, `+0x24` m_nPriority). Result on `Pier`: the client now gets its own player in every snapshot (16-17/s) and its position matches the server (e.g. server `815.7,1160.4`, client `815.6,1160.4`). The limit (found): CryNetwork collects a frame's unreliable data in a `CStream` with a fixed stack buffer, `DEFAULT_STREAM_BYTESIZE` 1124 bytes = 8992 bits (`CryCommon/Stream.h`; without an allocator `Resize` returns false). In `CryNetwork.dll` the constant `0x2320` occurs once, in the `CStream` constructor `FUN_34502810`. Writes past it are dropped silently.

Fix 2 (done, in the ASI): hook `CXServerSlot::SendUnreliableMsg` (`0x3306c620`, thiscall, `ret 0x10`, `m_pISSlot` at `+0xa3c`). During a snapshot, `XSERVERMSG_UPDATEENTITY` messages are counted against `SNAP_BUDGET_BITS` = 8000; once the budget is used up, the rest of the snapshot is held back (not sent), and these entities get their old `m_fLastUpdate` back, so their time-affected priority grows and they move to the front of a later snapshot. The client hooks `CXClient::ParseIncomingStream` (`0x3308354b`) to measure packets.

Result on `Pier`: server writes ~1815 updates/s, holds back ~1160, sends ~655; the client receives ~655 `UpdateEntity`/s (100% instead of ~40%), the biggest packet is 7928-8021 bits (< 8992), own player 16-17/s, positions match. Knob: `SNAP_BUDGET_BITS` (overhead seen ~20-100 bits, so up to ~8800 should still fit). Checked in game by the owner (2026-10-18, `Pier`): the client has its weapon and it fires; the rest works too. Open issues: occasional stutter; the crosshair does not turn red when aimed at an enemy (it does in the single-player campaign). `Training` (656 net entities) by the logs: ~680 updates/s sent and received, own player 17/s, biggest packet 7920 bits, positions match. Server crash on `Training` (owner, 2026-10-18): NULL read at `0x330cfe4a` in `CMovieUser::BeginCutScene` (`0x330cfd25`, `GameMovieUser.cpp`): it calls `GetISystem()->GetIInput()->GetIKeyboard()->ClearKeyState()`, and the dedicated server has no input. `EndCutScene` (`0x330cfed6`) does the same. Fix 3 (in the ASI): when `GetIInput()` is NULL both callbacks are skipped. Second crash at the same spot: NULL read at `0x3401a4eb` in `CryMovie.dll` (base `0x34000000`, PE timestamp `0x44ae37b4`): the cutscene sound track key handler `0x3401a396` calls `GetISystem()->GetISoundSystem()->LoadSound(...)`, and the dedicated server has no sound system. Fix 4 (in the ASI): skip only this sound key when `GetISoundSystem()` is NULL; the sequence itself keeps running on the server. Note: the handler is thiscall with 5 arguments (`RET 0x14`); the first hook build took 4 and corrupted the stack (crash at `0x3401046d`), fixed. Third crash at the same spot: `0x34013b53`, another CryMovie sound handler (`0x34013a7b`, same `GetISoundSystem()` pattern; several more exist). Fix 5 (in the mod, systemic): `coop_map` sets `mov_NoCutscenes 1`; `CMovieSystem::PlaySequence` (`0x34017ef9`) then does not start sequences flagged as cutscenes (flags `0x8`/`0x10`), so their sound and input code never runs on the server. Remote clients never saw these cutscenes anyway. Risk: a mission script waiting for a cutscene's end event could stall; not seen yet. Not yet verified at the cutscene.

Stutter: `SNAP_BUDGET_BITS` raised to 8800 (biggest packet 8755 bits, ~750 updates/s delivered, no loss). Measured the longest pause between snapshots (server) and TimeStamps (client) over 29 s on `Training`: 63-94 ms on both sides, so delivery itself is steady. Remaining suspect: each non-own entity gets only ~7 updates/s (750/s shared by ~110 active entities). AI on the dedicated server (owner, 2026-10-19: enemies stand still and do not see the client): not solved yet. Checked: `ESYSUPDATE_MULTIPLAYER` (passed by `CXGame::Update`) does not gate the AI update in `CSystem::Update` (`CrySystem.dll` `0x365151ce`); AI runs if `nPauseMode==0` and an unidentified cvar at `this[0xa18]` is 0. Server cvars: `ai_systemupdate=1`, `ai_ignoreplayer=0`, `es_UpdateAI=1`, `es_UpdateEntities=1`. Every `Player` entity registers as `AIOBJECT_PLAYER` in `Player:OnReset` (`player.lua`). Tried `es_VisCheckForUpdate 0` in `coop_map`: no change. `ai_noupdate` (CrySystem, `+0x2860`) is 0; the AI system itself runs (`CAISystem` `+0x1e4`=1, ~80 passes/s, logged by the ASI). Cause: the puppets are asleep on the dedicated server (a Lua tracer showed all 76 frozen); `AIEVENT_WAKEUP` + `AIEVENT_ENABLE` brings them to life. Fix 6 (mod, `Scripts/COOP/gamerules.lua`): once a second the server wakes puppets within 150 m of any player, except `bSleepOnSpawn` and hidden (`Enemy_Hidden`) ones. Verified on `Pier` by the tracer: behaviours `RunToFriend`/`CoverHold`/`RearAttack`, attention target = the player, enemies take damage and die.

## Spike 5 — host tools, client-side hits, map restart, saves recon (2026-10-19)

Host console commands (mod, `Scripts/Multiplayer/AvailableMods.lua`): `coop_goto [id]` lists the campaign checkpoints (`GameEvent` entities with `Properties.nId`) or moves all players to one and makes it the respawn point; `coop_spawn <n>` uses tagpoint `Respawn<n>`; `coop_god [0/1]`; `coop_ammo` refills every ammo type (`MaxAmmo` via `BasicPlayer.AddAmmo`); `coop_weapons` gives every weapon (9 slots, `PLAYER_MAX_WEAPONS`) — it needs all weapon classes loaded on the server before players spawn, because `CPlayer::m_mapPlayerWeapons` only holds the classes loaded at that time (`MakeWeaponAvailable` returned -1), so the COOP gamerules preload them; `coop_noclip [0/1]` (DevMode "designer fly mode", applied on the server and, through the `NOCLIP` server command, on every client); `coop_restart`. Lua 4 pitfall: `tinsert` adds a field `n`, so `for i, P in t` met a number and broke every command; `CoopPlayers` builds the table by index.

Map change/restart without dropping clients: the first `coop_map` uses `Game:LoadLevelListen` (starts the server), later ones `Game:LoadLevelMPServer` ("keeping the current clients connected", `ScriptObjectGame.cpp`). Verified: after `coop_restart` the client's world time resets and it keeps getting its own player 16-17 times a second, no menu.

Unkillable enemies / no red crosshair: the red crosshair is a hit flash (`Hud.hit=5` in `Player:Client_OnRemoteEffect`, userbyte 3, sent by `BasicWeapon.Server:OnHit` as `FX`; drawn by `Hud:DrawCrosshair` in `GUI/HudCommon.lua`), not aiming. A client tracer showed that every `FX 3` the client got came from AI shooters: the server never registered the remote player's hits (it sees `fire=1`, but the clip barely drops). Not root-caused. Replaced by client-side hits: the client hooks the global `ExecuteMaterial2(hit, effect)` (`CWeaponClass` caches each weapon's `Client.OnHit`/`Server.OnHit` at class load, `WeaponClass.cpp` `GET_VALUE`, so hooks on weapon tables never run), sets `Hud.hit=5` and sends `CHIT <id> <dmg> <part> <mat> <pos> <dir>` with `Client:SendCommand`; COOP `GameRules:OnClientCmd` applies it with `target:Damage(hit)`; `GameRules:OnDamage` drops server-side hits of remote players on AI. Server side verified with a simulated `CHIT` (170 -> 120 hp); client side not yet confirmed in game.

Saves recon: `CXGame::Save`/`LoadFromStream` return early when `IsMultiplayer()`. `SaveToStream` also needs a local client player (`m_pClient`, `CryError` otherwise) and the sound system (EAX preset), both missing on a dedicated server; `LoadFromStream` reloads the level through a local demo client and asserts a single server slot. Options: (A) real engine saves on a listen-server host: ASI bypass of the MP checks plus a custom loader that reloads with `LoadLevelMPServer` and restores entities without the single-player parts, large; (B) lightweight co-op checkpoint in Lua on the server: remember checkpoint, dead AI ids (static entity ids are stable across a reload of the same map), player ammo/health and mission objectives, then `coop_restart` and reapply; survives `coop_restart` (Lua globals persist), not a server restart unless written to a file. Recommended for testing: B.

Open bug: `GameEvent:OnTimer` (checkpoint save) reads `_localplayer`, which is nil on a dedicated server.

The COOP gamerules did not run at all on the first `coop_map` (only after `coop_restart`): the weapon preload loop at the top of the file met `WeaponClassesEx == nil` (on the first load the gamerules run before the weapon classes are defined), the Lua error aborted the file, and the engine kept the half-loaded rules without our `OnUpdate`, `OnClientCmd`, `OnDamage` and sequence forwarding. Fixed: the preload runs on the first `GameRules:OnUpdate`. Errors in these files do not show in `log_WinSV.txt`; check with a probe (`#dofile` of a script that logs the `COOP_*` globals).

Observed in game (Pier, Dam): the AI on the server works (mutants attack, damage reaches the player, the player dies and respawns, a gunship attacks the paraglider), the forwarded `heli` sequence reaches the client. Open: the owner sees enemies standing still while they move on the server; the owner got off the paraglider without wanting to; strong lag.

Monitor (`Scripts/COOP/Monitor.lua`, `coop_monitor [0/1]`): once a second the server (`MON S`) and each client (`MON C`) log the same lines: players (position, health, armor, weapon, ammo, vehicle), AI within 60 m of a player (position, health, behaviour, target), vehicles and helicopters within 150 m (position, driver), and events (death, respawn, weapon change, vehicle enter/leave, map load, sequences). `tools/mon-diff.ps1` compares the last 10 s of both logs by entity id (the two game clocks differ) and lists entities that are frozen on the client, off by more than 5 m, missing, or differ in health, weapon, vehicle or driver.

AI melee (2026-10-20): mutants ran up and stood still. The server deals AI melee damage only on the `KEYFRAME_APPLY_MELEE` animation event (`BasicPlayer.Server_EventHandler[ScriptEvent_AnimationKey]` sets `cnt.melee_attack`, then `CPlayer::UpdateMelee` raycasts and sends `ScriptEvent_MeleeAttack`), and a dedicated server never ticks character animations: no animation event arrives at all, even with `es_UpdateInvisibleCharacter 1`, `es_VisCheckForUpdate 0` or `entity:ForceCharacterUpdate(0)` every frame. The animations are loaded (`MELEE_ANIM_COUNT=3`, length 0.7 s). Fix in the COOP gamerules: every behaviour's `OnCloseContact` marks the entity, 0.35 s later the keyframe handler runs as if the animation hit (at most every 1.2 s, cancelled by a real keyframe), and the server sends `ANIM <id> attack_meleeN` so clients play the swing (AI animations are not replicated). Verified: mutants hit and kill, the owner sees the swing. AI jumps (`JUMP_TAKEOFF`/`JUMP_LAND` animation events in `CXPuppetProxy`, started from C++, not Lua) had the same problem: the AI "jumped" by walking and some got stuck. Fix 13 (ASI, 2026-10-24): hook at `0x330ba317`, right after the proxy registered both events; the ASI times the jump itself (take-off 0.15 s after its frame, landing one jump duration later, then `OnEndAnimation`, through the proxy's sink vtable) and sends nothing if a real event already came (`m_bInJump`). Seen on Cooler with fast mutants in combat: they jump up to ledges (up to +9 m, 20 m/s) and one that stood still before now moves. The clients get the new position only: the jump animation is not replicated (C++ `StartAnimation`, not wrapped). Any other animation-driven AI action is still missing.

## Spike 7 — area triggers on the dedicated server (2026-10-20)

Source: the owner's video "Far Cry Coop (Contest Island Invasion)" (youtube vqGOIem3d98, no captions; its description links Mixer's Contest Island Invasion and FlameKnight7's Assault Coop). The moddb build of Contest Island Invasion (v2.2.2.95) is a single-player campaign, not the co-op. Assault Coop v3 (`Downloads\assault-coop\v30`, unpacked to `Temp\assault-coop-v30`) carries Mixer's co-op change to `AreaTrigger.lua`. Its author forbids reuse of the scripts without permission, so only the idea is taken; our code is our own.

Finding: `AreaTrigger` (and every other shape-area entity) fires only for the machine's own player: `CPlayer::Update` calls `m_XAreaMgr.UpdatePlayer` only when `IsMyPlayer()` (`XPlayer.cpp:842`, "areas are only used for the local player (they will not trigger things on the server)"). On our dedicated server no area trigger ever fires, so missions that advance on "reach this place" stall. Proximity triggers (entity trigger boxes) are not affected.

Fix 7 (mod): `COOP/ClientStuff.lua` `CoopWrapAreaTriggers` (from `ClientStuff:OnInit`) wraps `AreaTrigger.Empty.OnEnterArea`, `Empty.OnLeaveArea` and `Occupied.OnLeaveArea`: a remote client sends `TRG <id> 1/0` for its own player and skips the local trigger logic (the server forwards HUD and sequences, so they would show twice); a server runs the original. `COOP/gamerules.lua` `CoopClientTrigger` runs the trigger's state function for that player with `_localplayer` set to it; leave counts only for the player who entered (`Who`). Monitor event: `area <trigger> 1/0 <player>`. Not verified in game yet; risk: if the engine copies state tables per entity, the class-level wrap misses entities that already exist (then the monitor shows no `area` events).

Result (owner, Training, first village): nothing changed. A class-level wrap did not reach the triggers, so each `AreaTrigger` instance is now wrapped in `ClientStuff:OnInit`. A client probe (`Temp\probe-area.lua`) confirmed the wrap: 4 triggers near the player, `wrapped=1`, our function in place, the state table shared with the class. Still no `OnEnterArea` at all on the client, not even on a root handler. So a remote client gets no area callbacks, and the client relay (Mixer's idea) does not work on 1.4 with stock maps. The village AI have `bSleepOnSpawn=1` and wait for `AreaTrigger80` (9 m from the player, `in=0`).

Assault Coop analysis: its 7 campaign maps were re-edited ("many triggers need to be newly placed"); mission logic runs mostly on `ProximityTrigger` boxes (physics, server-side, `bOnlyPlayer`), area triggers only through the client relay. Sleeping AI are woken by trigger events (`BasicAI:Event_Activate`), as in stock. Nothing there that makes stock area triggers fire on a server.

Next: in the ASI, let the server update areas for every remote player (`CPlayer::Update` runs `m_XAreaMgr.UpdatePlayer` only when `IsMyPlayer()`; anchor string `CPlayerUpdate::XAreaMgrUpdatePlayer`). Then the client relay can go.

## Spike 8 — checkpoints, paraglider exit, server frame rate (2026-10-20)

Checkpoints: the client always respawned at the map start. `GameEvent:OnTimer` (a mission save trigger's `Save` event) reads `_localplayer`, nil on the dedicated server, so `_LastCheckPPos` was never set and `GameRules:RespawnPlayer` fell back to the first spawn point. COOP gamerules wrap each `GameEvent`'s `OnTimer` (once a second, per entity) to run with the nearest living player as `_localplayer`; monitor event `checkpoint <name> at x,y,z`. Not yet seen in game: the paraglider bug below kept the server from reaching the save trigger.

Paraglider: the server dropped the player when `Gunship1` flew into the paraglider (`Paraglider:OnContactServer`: a collider other than the driver means everyone out), but the client kept gliding: `Paraglider.Client` has no `OnUnBind` (every other vehicle has `VC.OnUnBind`), and patching it on the client did not help. The server now broadcasts `VEHOUT <vehicle> <player>` from a wrapped `VC.ReleaseUser`, and the client releases that seat itself. Verified: the client gets out together with the server. With the client gliding on, the server had counted triggers along its own, different path (`saveTrigger56` fired only on the client).

Gunship and props are not synced: level entities spawn with `ed.netPresence = false` (`XSystemBase.cpp`); only players, AI and vehicle-class entities (`CVehicle` calls `SetNetPresence(true)`) are ever sent. `Gunship` (class 102, `AI/Gunship.lua`) is not a vehicle class: it flies on the server and stays at its start on the client; pushed barrels never move there. Giving net presence to every entity that moves on the server broke respawn: the client then gets updates for entities it never created (`entity 3 updated but not spawned`), and `CXClient::OnServerMsgUpdateEntity` returns false, which drops the rest of the packet, the own player's updates included. The client also asks for 50 updates a second (`Client:SetUpdateRate`, again in `OnSetPlayer`: asked only in `OnInit`, it was lost), and the server no longer broadcasts AI idle animations (`ANIM ... idle*`, ~5 reliable messages a second).

Rejected: a CryGame.dll rebuilt from the 1.4 SDK. It needs VC 7.1 (Visual C++ Toolkit 2003) and the SDK's STLport 4.6, because STLport strings cross every engine interface (`CrySystem` reads `ISystem::LoadConfiguration(const string&)` as STLport); with VS 2022 or MS STL it crashed. It ran with both, but each round was a slow rebuild, it disabled `FarCry.WidescreenFix.asi` and our own ASI, and gave no gain the owner could see. Fixes stay in the ASI.

Monitor: `moved <id> <name> <class>` for loose objects within 15 m of a player whose position changed.

Fix 10 (ASI): an entity of class `RigidBody`, `DestroyableObject` or `BasicEntity` (the barrels and crates of Pier) gets net presence once it moves on the server; `GetClassId` is at `+0xe8` of the `IEntity` vtable (`cmp ax, class id` right after it at `0x33071930`). No client packet failures with it, and respawn works (the owner can crouch and fire after dying). With `Gunship` in the list the gunship did reach the client, but flew in jerks; the owner chose to leave it out.

## Spike 11 — campaign saves for the host (2026-10-22)

The engine's `CXGame::Save` and `LoadFromStream` return early in multiplayer, so the saves are a Lua save (option B of the saves recon), kept in a file so that it survives a restart of the game: `Mods\FarCryCoop\save_<name>.lua`, a Lua table (`COOP_LoadedSave = {...}`) written with `writeto`/`write`, read back with `dofile`. It holds the map, for each player the position, angles, health, armor, weapons, current weapon and ammo, the ids of the dead AI (static entity ids stay the same when the map reloads), and the respawn point (`_LastCheckPPos`). A dead player is saved alive. Not saved: mission scripts, triggers, pickups, vehicles. After a load the mission script starts from the beginning of the map, with the dead AI removed (`Server:RemoveEntity`; there is no `System:RemoveEntity`) and the players put back.

- **Autosave:** a checkpoint (`GameEvent`, a save trigger) calls `Game:OnAfterSave` after it set `_LastCheckPPos`; the COOP rules wrap it and save as `auto`.
- **Quicksave / quickload:** F6 / F7 on the host (`Input:BindCommandToKey`), saves as `quick`; or `coop_save` / `coop_load`.
- **By hand:** `coop_savegame <name>`, `coop_loadgame <name>`.
- **Load:** with a game running, `CoopLoad` sets `COOP_PendingMap` and `COOP_PendingLoad`; `GameRules:OnUpdate` calls `CoopMap` (`LoadLevelMPServer`, joined players stay connected), and `CoopApplyLoad` runs once every player has spawned (it waits up to 30 s for a client that is still respawning, so the client is placed too). From a fresh start, the launcher lists the files as maps called `save:<name>`; the host's line is `CoopLoad("<name>")`, which starts the server with `CoopMap`. Friends join as usual and spawn at the saved respawn point.
- The weapon code of the level carry-over (`CoopCollectLoadout`, `CoopGiveLoadout`) is shared with the saves.

Verified in game (Pier, two games on one PC): `CoopSave`, then `CoopTeleport` 60 m away, then `CoopLoad`: the host and the client are back on the saved spot; a checkpoint creates `save_auto.lua`; the launcher starts a game from `save:t2` and both players appear on the saved spot. Not verified: the F6/F7 keys (no keyboard in the test), the single-player "Load Game" menu (not connected: it loads single-player saves), a long mission played through after a load.

**Mission state in saves (version 2, 2026-10-22).** A save now also keeps what the single-player save keeps for the mission (`CXGame::SaveToStream` writes every entity's state, its hidden flag and calls its script `OnSave`):
- **Gone level entities.** The ids of the level entities (static ids, below 32768) that exist at save time. After the load, every level entity that was not there is removed again: picked-up items (a pickup without respawn removes itself), removed AI, objects.
- **Living AI.** Their position, heading and health.
- **Triggers, doors, mission hints.** `AreaTrigger`, `ProximityTrigger`, `ProximityKeyTrigger`, `DelayTrigger`, `MultipleTrigger`, `AITrigger`, `VisibilityTrigger`, `Door`, `AutomaticDoor`, `MissionHint` keep their state through their own `OnSave`/`OnLoad`. These are called with `CoopStm`, a stand-in for the stream that writes the values into the save table. A fired once-only trigger stays fired, so the mission does not repeat it.
- **Hidden entities** (`COOP_HideState`, restored through the wrapped `Event_Hide`/`Event_UnHide`, so clients follow) and the **mission objectives** (restored through the wrapped Hud: the clients get the same list).

Old saves (version 1) still load as before. Not saved: the level script's own `Mission` variables, AI behaviours, vehicles, and players, AI and vehicles' own `OnSave` (heavier, left out).

Checked on Training with two games: an item removed, a `ProximityTrigger` and an `AreaTrigger` set as fired, an AI moved 7 m with 42 health, two objectives (one completed). Then `CoopSave` and `CoopLoad`. After the reload the entity tables are new (a mark set before the save is gone), and everything is back: the item stays gone (on the client too), both triggers fired, the AI on the saved spot with 42 health, and the objectives on the host and the client. Log: `mission state: 1 entities removed, 145 states restored, 2 objectives`. Seen once: `loaded t5: 1 players`, i.e. the load was applied before the client had respawned, so the client was not put on its saved spot (this was so before as well).

What the ASI logs now (`PHYSICS ERROR` in the netlog; the hook is at `CryPhysics.dll` RVA `0x52d0`, the printf-like error reporter): the message comes from `FUN_3509b880`, the reader of a rigid body's state (called by `FUN_3509c9b0`, a `SetStateFromSnapshot`-like function), not inside a network entity update (`in entity update: 0`). `ReadPacked` reads a packed number and complains if it is above 16; it read 20, so the stream is out of step or an entity has more than 16 parts. Swallowing the message only moves the failure one read on (`CStream:ReadNumberinBits int 40>32`). Not checked without the mod: there was no way to start a single-player level from a script (`StartLevel`, `map` and `+map` did nothing there).
  **Cause and workaround (found the same day).** A hook on `CryPhysics.dll` `SetStateFromSnapshot` (RVA `0x9c9b0`) names the entity: on Treehouse entity 410, a `BasicEntity` at 1082,1457,62. Its caller is `SetStateFromSnapshotTxt` (RVA `0xc2fd0`): some level entities carry a physics state baked into the level file as text, which is turned into a `CStream` and read by the rigid body's reader; the reader finds 20 parts where it allows 16. Ignoring the error only moved the crash (an access violation at `0x350050b1` in `CryPhysics.dll`). So the ASI does not apply a baked state in a co-op game (a game that ran a `CoopMap(`, `CoopLoad(` or `Game:Connect(` line; `baked physics state skipped` in the netlog): the object stays where the level file puts it. Result: Treehouse, Swamp, Factory, Dam and Volcano load for both games and the checkpoint hops work (gap 1-3 m); the two exceptions, Swamp checkpoint 4 (client 1087 m away) and Volcano checkpoint 3 (44 m), are the late client of [issue #3](https://github.com/Bantila/FarCryCoop/issues/3). Not known: why the text does not fit the reader, what the skipped states looked like in the game (the screenshots of the sweep were black), and which other levels had baked states that are skipped now.
- **Bunker -> Steam: the host crashes, reproduced 2 of 2.** No error window, the process is gone. The ASI's fault log: `exception c0000005 at 36505c3e`, reading `0x6e696f50` (the ASCII "Poin"). That address is in `CrySystem.dll`, in the C runtime's small-block allocator (`FUN_36505c27`, taking the head of a free list): a free list was overwritten with text, i.e. heap corruption during the level change. Who writes it is not known. A fresh launch of Steam is fine.
- **Boat:** in the sweep the client was gone after Cooler -> Boat (the server had only the host's player; Boat, Catacombs and River without the client). Not reproduced: a second Cooler -> Boat run kept both games alive.
- **Level change: random host crash, more data (2026-10-22).** It is not specific to a map pair or to the client: Cooler -> Boat with the host alone crashed 2 of 5 runs, then 0 of 14 after the ASI was rebuilt (the only change: a deeper fault log), with the client 1 of 4 and 1 of 2; Bunker -> Steam crashed 2 of 2 at first, then 1 of 6. A captured stack (the ASI's fault log now lists the code addresses on the stack) is all in `CrySystem.dll` (`0x36506xxx` the allocator, then `0x3652xxxx`-`0x36573xxx`, which looks like the pak/file code): the allocator trips over a free list that something else corrupted earlier, so the writer is not on the stack. Unknown if the unmodded game does the same on a multiplayer level change. Ideas: the same map change in the unmodded game's multiplayer; force the CRT onto the system heap (`__MSVCRT_HEAP_SELECT`) and use page heap to catch the writer; as a mitigation, restart the game process for a level change and load the autosave.
  **Cause and fix ([#2](https://github.com/Bantila/FarCryCoop/issues/2), 2026-10-22).** The allocator that crashes is not the C runtime's: `FUN_36505c27` (alloc, free lists at `0x365888c0` indexed by `(n-1)>>3`, refill for an empty list) and `FUN_365055c8` (free) are STLport's node allocator, statically linked in `CrySystem.dll` for blocks up to 128 bytes (bigger ones go to `malloc`), and it takes no lock. A probe in the ASI (log every call from a thread other than the main one) showed a second user: `CrySoundSystem.dll`'s streaming thread (return addresses `0x3600xxxx`, `0x360329aa`; sound file names like `p_01s_01` on its stack) opens files through CryPak and builds STLport strings in CrySystem. When it and the main thread pop or push the same free list at once, one block is handed out twice, and a string written into it ends up as the free list's "next" pointer: the text in the crash. A level change loads many sounds while the main thread loads the level, so it is hit there. Fix 12 (ASI): both functions run under one critical section; the netlog writes `node allocator: thread N waited for another thread` whenever a thread had to wait (each a collision without the lock). Result: Bunker -> Steam with the client 8 of 8 alive (before 3 of 11 crashed); the host waited in 4 of the 8 runs (10 times in all), so collisions do happen on every few level changes. Not checked: whether the unmodded game does the same (it should: the code is the engine's); other DLLs have their own STLport allocators, no crash points there yet.
- **Factory, Dam, Volcano:** no data in the first sweep (it stalled at Swamp); after the workaround all three loaded in a sweep and the checkpoint hops worked.
- **Bunker:** one Lua error, once: `AI error in DEFAULT.CONVERSATION_REQUEST: attempt to index field CurrentConversation (a nil value)` (our wrapper of the AI behaviours logs it).

**Vehicles with fewer seats than players ([#5](https://github.com/Bantila/FarCryCoop/issues/5), 2026-10-22).** Seats by class (driver, gunner, passengers up to `passengerLimit`): Paraglider 1, Buggy 2, Boat 2 (driver and gunner), InflatableBoat 2 (with `CoopBoatSeats`), Forklift 1, FWDVehicle 7, Bigtrack 10. Swamp's `Val4WD` is an `FWDVehicle` (`mission_swamp.xml`, entity 272): Valerie drives, a gunner and 5 passengers fit, so 4 players do. The paraglider copies are now general (`CoopVehicleCopies`, replaces `CoopParagliders`): for Paraglider, Buggy, Boat and InflatableBoat, once players sit in one and every seat is taken, and no vehicle of that class from the same start spot (20 m) has a free seat, a copy is spawned on the start spot, until those vehicles have a seat for every player. It waits until the spot is clear (nothing of that class within 6 m), because a car spawned inside one that still stands there would blow up. The position is passed to `Server:SpawnEntity(class, pos)`: with a `SetPos` after the spawn the client had the copy at 0,0 (an empty vehicle sends no updates). Not copied: FWDVehicle, Bigtrack (enough seats) and Forklift (mission puzzles). Checked on Training with two games and a faked player count (seats filled in the vehicle's tables, `CoopPlayers` returning 3 or 4): 2 players and a full buggy, no copy; 3 players, one copy on the buggy's start spot, the client sees it there; 3 and 4 players again, no second copy. Not checked: real 3-4 player games (only 2 games run on one PC so far), boats.

**Helicopters (Pier).** The 6 helicopters (5 `Gunship`, one `V1`) exist on both sides: every client spawns them from the level. At rest they do not move on the host. On the client they hover 8-34 m higher than on the host (a local simulation, +-2 m). When the host moves one (`SetPos` +40 m), the ASI gives it net presence (`netPresenceIfMoved`) and the client is on the same spot at the first sample (gap 0 m, held for 28 s). ## Steam inside the game (2026-11-13)

The Steam bridge moved into the game process: `asi/steam.c`, included by `FarCryCoopNet.c`. There is no separate `FarCryCoopSteam.exe` window any more, and Steam runs as Far Cry (AppID 13520, owner's decision; `SteamAppId`/`SteamGameId` are set in the environment, as Steam does when it starts the game), not Spacewar. The tunnel is the bridge's: the game still talks UDP on 127.0.0.1 (server 49001, client 49011), and a Steam thread moves those packets over `ISteamNetworkingMessages` (NAT punch, else Valve relays).
- **On/off.** On when `Mods\FarCryCoop\Steam\steam_api.dll` exists (x86, Steamworks SDK redistributable; the release ships it there). Without it nothing changes: no thread, no console hook. `Mods\FarCryCoop\steam_loop.txt` turns on the loop transport instead of Steam: the "Steam" between two games on one PC is UDP (host 49021, clients 49022+, an id is that port). The harness writes it with `up -steamloop` and removes it at `down`.
- **Host.** Every 2 s the Steam thread asks `GetExtendedUdpTable` whether this process holds UDP 49001. Then it sets the rich presence `connect` (`+coop <SteamID>`), so friends get Join, and marks its lobby `up=1`. Sessions are accepted only from Steam friends or members of the host's lobby, and only while the server runs.
- **Client.** Join from the friends list (`GameRichPresenceJoinRequested_t`), a lobby invite (`GameLobbyJoinRequested_t`), the command line when Steam starts the game for a Join (`+coop <hex>`, `+connect_lobby <id>`), or `coop_steam join <hex>`: the tunnel binds 127.0.0.1:49011 and the main thread runs `#Game:Connect("127.0.0.1:49011",1)`.
- **Console.** `coop_steam status | join <hex SteamID>|loop | host <max>|key=value|... | find | joinlobby <n> | leave | invite`. Caught in `IConsole::ExecuteString` (CXConsole vtable slot +0x80 replaced), so it works typed and from Lua (`System:ExecuteCommand`). The Steam thread queues its console output and lines to run; `hGameUpdate` prints and runs them on the main thread. All Steam calls stay on the Steam thread (manual callback dispatch).
- **Lobbies.** `host` creates a public lobby (`k_ELobbyTypePublic`, up to 16) with the given key=value pairs and then ours, which win: `fc1coop=<net key>`, `host=<SteamID>`, `up`. `find` asks for the world list with that key; `joinlobby <n>` enters a lobby and connects to its `host` once `up` is 1 (not to the lobby owner: Steam passes ownership to another member when the host leaves). The host's lobby and the lobby a client entered are kept apart; a game that runs a server refuses lobby invites. Lobby strings are other players' input: printed cut (`%.48s`), never put into a console line to run.
- **Who gets in.** A public lobby lets anyone who finds it in the world list become a member and so get a session (owner's choice: public games, spec). Passwords and friends-only games are not done yet (menu step); an accepted session is not checked again when the player leaves the lobby. The menu (spec `docs/specs/in-game-menu.md`, step 3) will drive these commands from Lua; `CoopSteam_OnLobby` is called when a lobby is created.
- **Review (fresh-context subagent, 2026-11-13), fixed before the commit:** a remote lobby name could overflow the list line (1 KB into a 400-byte buffer); lines to run shared one queue with prints and could be dropped; `host` blocked the tunnel while waiting for Steam; one lobby variable served both the host's and the joined lobby; with Steam off `coop_steam` lines vanished silently (now: a console line and `CoopSteam_OnLobby(0)`); a client refused a session restart from its own host.
- **Checked (2026-11-13, one PC).** Loop: `tests/steam-loop.txt`, the client's only join line is `coop_steam join loop`; it joined through the tunnel (`player 00000bf7e joins` on the host), 653/653 entities matched, 43 snapshots/s. Real Steam (logged in, one game): init under 13520, relay status 100, `coop_steam host 4|name=Test game|map=training` created a lobby and `coop_steam find` listed it (`Test game | training | 1/4 | up=1`). Not checked yet: a second Steam account on another PC (Join, lobby join, relayed traffic between two accounts).
- **Launcher.** It no longer starts `FarCryCoopSteam.exe` (an old copy left by an upgrade would take UDP 49011 from the game). The bridge source stays in `steam/` until the menu replaces the launcher.
